Section 3 · The product you built on

CALL-E explained simply

CALL-E is an AI agent that makes phone calls to get a job done. You don't design a dialogue tree. You give it a goal in plain language, a phone number, and optionally a result schema (the JSON shape you want back). It plans the call, dials, talks, and returns a summary, a transcript and structured data.

Ways to use it

  • Web app / dashboard (heycall-e.com): type a goal, it calls. 100 free credits (≈ US$1) on sign-up. API keys live at dashboard → account → API keys.
  • Developer API + SDKs (Python calle-ai, TypeScript @call-e/calle): create a call, get the call, read events, cancel. You used this.
  • CLI: calle auth login.
  • MCP (for AI agents like Claude/Cursor): plan_call → run_call → get_call_run. No webhook_url, so it relies on polling.
  • ChatGPT app, published by AI Rudder Pte Ltd.

Capabilities to name-drop

  • Smart goal clarification: asks for missing details before dialing
  • Structured, schema-validated results
  • Scheduled and batch calling
  • Real-world voice handling: voicemail, screening, hold, transfers, interruptions
  • IVR navigation with DTMF keypad tones
  • Governance: rate limits, concurrency controls, blocklists, kill switches, audit trails

The role: Technical CSM + Forward Deployed Engineer

This is a hybrid role. The Technical CSM half owns the customer relationship and outcomes. The Forward Deployed Engineer (FDE) half sits with the customer and writes the code that makes the product work in their real systems. In practice: you scope it, build it, ship it, prove it works, and keep it working.

Technical CSM half

Owns the customer & the outcome

  • Discovery: goals, KPIs, volumes, compliance, who signs off

  • Health monitoring, escalations, QBRs, ROI vs control group
  • Expectation-setting: says honestly what the product can't do yet
  • Renewal and expansion: “evidence to expand”
Forward Deployed Engineer half

Builds the solution in the customer's world

  • Writes integration code: CRM/core-banking APIs, webhooks, data mapping, list uploads
  • Designs agent configs: task prompts, result schemas, routing rules
  • Debugs in environments you don't fully control (customer network, CRM, telephony)
  • Prototypes fast, then hardens: tests, idempotency, retries, monitoring
  • Turns repeated custom work into product feedback (“we built this for 3 customers → should be a feature”)

Section 7 · What you built

Your project in plain English

Financiera Solaria (fictional consumer lender in Mexico) wants an AI agent to call customers 3 days before an installment is due, remind them in Mexican Spanish, and record one actionable outcome in the CRM, such as “promise to pay on Fri 9 Oct”, with a follow-up task for the right team.

Why this scenario

Most late payers aren't unwilling. They forget, or get paid after the due date. Human agents waste hours on calls that end in “I'll pay Friday”, and the promise ends up in free-text notes nobody can check.

Boundaries (what the agent will NOT do)

No negotiation, discounts or payment plans. No taking payments or card data. No talking about the debt with anyone but the account holder. No legal threats. No automatic redial. Anything that needs judgment becomes a task for a human.

The six steps (memorize these)

  1. Read the account from the CRM (name, phone, amount, due date, time zone). Guards block the call if there's no valid phone, a do-not-call flag, or it's outside 08:00–21:00 customer local time.
  2. Create the call on CALL-E: task prompt + result schema + MX/es-MX + metadata, with an idempotency key saved before the request, so a crash or retry can never call someone twice.
  3. CALL-E has the conversation in Spanish: AI disclosure, identity check, reminder, asks for a date, handles exceptions.
  4. Webhook arrives. It's unsigned, so it's only a wake-up signal. Checks: header event id = body id, and the call id must be one we created.
  5. Re-read the call from the authenticated API (GET /calls/{id}). That is the source of truth. A forged webhook body can't fake a promise.
  6. Business rules turn the verified result into a CRM status + task + team. The write goes through an outbox and only counts when the CRM answers 201 created (or 200 duplicate).

Section 9 · The three layers

Who decides what: the three layers

CALL-E is goal-driven: you give it a task and a result_schema, and it plans the conversation itself. That makes it important to be explicit about which behaviour sits in which layer.

1 · Instructions

The task prompt: purpose, AI disclosure (“virtual assistant Sofía”), right-party check before mentioning the debt, clarify a vague date once, exception handling, and a NEVER list (threats, discounts, card data, claiming to be human).

File: agent_config.build_task. The exact text any call received: Results → the call → “Request sent to CALL-E”.

2 · Workflow config

The contract with CALL-E: result_schema with string enums that each include unknown, ISO promise_date (“never guess”), promise_certainty firm/tentative, verbatim outcome_evidence; region/locale; metadata; idempotency key.

File: agent_config.RESULT_SCHEMA.

3 · External logic

Your tested code: guards.py (who and when) and outcomes.py (what an answer means: status, task, team, priority, SMS). No auto-redial.

A promise only counts if it's specific, firm, and at most 7 days after the due date.

The principle in one line

“The voice agent reports what happened; the customer's code decides what it means. Prompts are probabilistic, so anything with a compliance or money consequence is enforced in code I can test.”

Section 10 · The content pipeline

How the goal, strategy, script and call list become a phone call

The call list

Lives in the CRM (mock, :8001), seeded from data/seed_accounts.json — 8 fictional customers. "Run campaign" reads the whole list; the guards then decide who may actually be called (phone present and valid, not do-not-call, 08:00–21:00 local). To change the list, edit the seed file and press Reset. "Call my phone" just points María Fernanda's row (ACC-1001) at your number for one live test.

The goal and the script

Never typed into CALL-E's website. They are a template in code — agent_config.build_task() — filled with each customer's own data:

You are Sofía, a virtual assistant (AI) calling
on behalf of Financiera Solaria...
STEP 2 - ask the person to confirm they are {full_name}.
STEP 3 - installment #{n} for {amount} is due on {due_date}.
EXCEPTIONS - human requested, dispute, hardship, paid...
NEVER: threaten · take card numbers · claim to be human.

Read the exact text any call received: Results → the call → "Request sent to CALL-E". To change the script, edit that file and restart ./run.sh; the next call uses it.

The strategy (three owners)

  • Who and when — your code: guards, calling window, one-call-per-cycle idempotency.
  • What to say and never say — the task text above.
  • How each sentence is said live — CALL-E's engine. There is no word-for-word script: it improvises within your rules, which is exactly what makes it handle real people.

The answer form (RESULT_SCHEMA) closes the loop: it tells CALL-E which fields to bring back — fixed lists with an unknown option — and your rules turn that into a CRM status and a task.

Tests and the before/after story

The 4 required tests

  • T1 Normal: firm promise → promise_to_pay + verify task + SMS ✓
  • T2 Ambiguous: “a fin de mes, si me pagan” → needs_review. v1 FAILED
  • T3 Integration failure: CRM 503 → honest pending → retry → 1 task. v1 FAILED
  • T4 Exception: asks for a human → high-priority callback ✓

What you fixed (commits 270ed09 → 24ac420)

  • False promise: v1 trusted outcome=promise_to_pay. v2 requires a specific ISO date + firm + ≤ due+7 days.
  • False success: v1 answered 200 synced while the CRM write had failed, so the result was silently lost. v2 adds the outbox and the honest 202.
  • Retest: all pass. Today: 39 automated tests (.venv/bin/python -m pytest -v).

The before/after story (your strongest evidence, ~40 s)

“My first version failed two of the four required tests. A vague ‘end of the month, if I get paid’ was recorded as a firm promise, which would have sent a payment link and corrupted the forecast. And when the CRM was down, it still said ‘synced’, so the result would have been lost silently. I fixed both: a promise now needs a specific, firm date within policy, and CRM writes go through an outbox. Success is only reported when the CRM confirms it. Then I retested, and everything passes. The git history shows both versions.”

The three decisions (D1–D3)

D1

Rules in code, not in the prompt

Why: prompts are probabilistic; money/compliance decisions must be testable and auditable. Evidence: T2. Trade-off: some genuine promises land in needs_review (agent time). Would change if: live accuracy is very high and review volume overloads agents. Then relax the rule (e.g. accept tentative within 3 days), not move it into the prompt.

D2

Webhook = signal, API = truth, outbox

Why: webhooks are unsigned, may repeat or not arrive; the CRM can be down. Alternatives: trust the body (forgeable) or poll only (doesn't scale). Trade-off: one extra API read per call; more moving parts. Would change if: CALL-E signs webhooks, or the CRM offers idempotent upserts/queues.

D3

Narrow scope

One reminder call; no negotiation, payments or auto-redial; judgment → routed human task; mock CRM over real HTTP (so outages can be demoed on demand). Trade-off: less automation per call. Would change if: pilot shows most human tasks are routine, or Solaria approves a payment-plan policy. Add one capability at a time, each with its own test.

“Why not let CALL-E decide the outcome?”

“It does extract the outcome. My code decides what it means for the account. That way compliance and finance can read and test the policy in outcomes.py, it's the same in live and simulated mode, and I can change the policy without re-prompting.”

Section 16 · Is it ready?

Readiness, rollout and metrics

“Is it ready for a pilot?”

“Yes for a small, controlled pilot after a 1–2 week pre-pilot of internal test calls. Not for full volume yet, for two reasons: live Spanish extraction accuracy isn't proven, and Mexico is on an international line, which CALL-E itself says is intended for development and testing. Phase 1 · Pre-pilot · 1–2 weeks

30–50 internal calls to employee phones playing personas. Measure extraction accuracy against human labels. Legal review of the script.

Phase 2 · Pilot · 4 weeks

500–1,000 low-risk accounts (upcoming due, not delinquent). A/B against SMS-only. 100% human QA on needs_review + 10% sampling of the rest.

Only if promise-kept and on-time-payment rates beat the control over 2 billing cycles, accuracy is above target, there are no compliance incidents, and the human workload fits the team.
